# Repeated semantic families

Use this procedure only when multiple profiles or records repeat the same
semantic contract with fixed per-instance data. Similar file shape alone is not
enough. Treat a changed invariant, authority rule, failure mode or acceptance
meaning as a new semantic family.

1. Compare the profiles and name the shared semantics and the per-instance
   command/data fields. Preserve each historical record as immutable evidence.
   Do not rewrite old reviews to imply they covered a later common contract.
2. Settle one sealed common contract for the family. Name assumptions, input
   bindings, bounds, proof obligations, failure behavior and exact evidence.
   A shared builder may make deterministic instances, but must not change
   acceptance, infer missing authority or relax caps, bounds or proof checks.
3. Review the common contract once. Then have the routine reviewer independently
   inspect each exact generated command and data delta for correct binding and
   execution. Reuse archived evidence only for identical inputs, hashes and
   covered scope; retain the evidence link for each instance.
4. Escalate a named assumption or semantic change for focused authority review.
   Do not repeat full contract review for unchanged instances, and do not reduce
   review merely because a profile looks similar.

Keep the task's accepted base and authorization across a resume. Continue with
the same saved session budget. A new session or budget is a new round and needs
explicit authorization. This procedure changes review reuse only; it does not
authorize new work, weaker acceptance or a different budget.
